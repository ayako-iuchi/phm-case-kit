- `calccheck.py` recalculates a register of numbers taken from a document, with exact arithmetic and a formula parser (no Python evaluation). It compares each derived number with the number shown, at the precision shown, and, for a number whose calculation the document does not give, tries each recorded reading (`candidate`). It reports `MISMATCH`, `NOREPRO` and `UNRESOLVED`, and register problems R1–R5.
- `register/calc_hcs17_25.tsv` records the business-plan outline template Hypothetical Case Study #17.25 (fictional, written by the author with generative AI): 45 rows, one of them a value printed in a table of #17 (p. 7, an image) and copied as printed. The run reports one `MISMATCH` (the benefit rows sum to 2.965, the total shown is 3.32), one `NOREPRO` (no recorded reading gives the payback period of 1.5 years: 0.96, 1.08, 1.10, 1.26, 1.90 and 2.05 years) and one `UNRESOLVED` (a reading of year 2's benefit needs a ramp-up factor the document does not give).
- A first review by a separate agent that had not written the kit found that calccheck stopped with a traceback on a row with a formula but no id, that seven candidate rows did not say in their notes that they are readings, and that one note (pb_shown) attributed a division to #17 that #17 does not show. Fixed before release: rows without a valid id are reported as R1; deep nesting, long formulas, very long values, large `places` and very long dependency chains are reported instead of stopping the tool; a row that only depends on a row with a register problem, a loop or a division by zero is not reported again; every candidate note now begins with 「読み」 (reading); notes on pb_cf_a and pb_cf_b give the [X] cells taken as 0; b1_17 cites the total printed in #17's table; payback quotes how #17's tables describe the 1.5 years; alpha2's `shown` is now `-`. Three tests were added.
- A second review found that a long sum within the formula limit, or a very large calculated value, still stopped the tool, that the result for a deep chain depended on the order of rows, and that a number whose candidates all failed on register problems still got `NOREPRO`. Fixed before release: formulas are evaluated without recursion and rows in dependency order; a calculated value past 4,000 bits is R2; such a number gets no `NOREPRO`. Both READMEs now say that version 1.4 is in preparation. Two tests were added.
- A third review found no must-fix. Fixed before release: rows in a loop are found as strongly connected groups, so every row in a loop gets R3; every operand is evaluated, so a division by zero or a value past the limit is reported whatever the operand order; a row with its own register problem is not checked for `MISMATCH`; `NOREPRO` names candidates that could not be calculated; a sentence in both READMEs that ran R5 into the R2 and R3 notes. One test was added.
